4 · AI design — proposal and implementation: how it works

Constrain the model to approved content and own-record context, then test its answers

The coach, step by step

1 · Who is asking. Clerk identity maps to D1 membership. The API supplies own-record context; real Clerk sign-in is proven across all three roles.

2 · Guardrail layer 1, before any model call. Rules catch colleague data, pay and promotion, prompt injection, wellbeing and crisis. National ID, phone and email are masked.

3 · Retrieve approved sources. Sandbox: Thai segmentation + BM25 over lessons and policies. Proposed production: multilingual embeddings and transcripts.

4 · Layer 2, then the answer. When enabled, a classifier checks intent. Answers cite [S1], [S2]; unsupported requests abstain. Final metadata identifies fallbacks.

5 · Blocked topics get fixed safety replies. These point to the manager or HRBP, the EAP, or the 1323 crisis hotline. Review these templates with the client before launch.

The path engine

  1. Rules shortlist catalogue items by skill, level and format. A 2 h/month learning budget is a production acceptance target.
  2. The LLM puts them in order and writes a reason for each step, in Thai and English.
  3. Catalogue IDs are validated. Guaranteed critical-gap coverage still needs production validation.
  4. The manager approves. Production batch generation and any discount remain planning assumptions to verify.

Thai, done properly

  • Thai has no spaces between words, so search needs word segmentation, not plain keywords.
  • Polite register (ค่ะ / นะคะ), Thai-English mixing (SBI, OEE) and a company glossary.
  • Native-speaker review is a required production gate. On-shore Thai models (Typhoon, ThaiLLM) are an option later for simple tasks.

Core sandbox implementation; live AI gate remains unpassed

5

The core design choice: the model chooses from a menu we control and never writes the menu. The path engine can only order catalogue items that the rules already shortlisted, and its output is checked against real IDs. The server decides which personal data it sees. Source constraints reduce risk; they do not prove that a live answer is grounded. The failed live report remains visible.
